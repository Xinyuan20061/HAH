# HealthMate 创新性与竞争力开发实施方案

> 版本：2026-09-28  
> 状态：实施规格与验收计划；本文中的目标值不是已取得的成绩，也不是赛事官方评分标准。  
> 当前事实来源：[功能汇总](HEALTHMATE_FEATURE_SUMMARY_2026-09-28.md)、[验证记录](VERIFICATION.md)、[动作全量报告](../benchmark-results/motion-v1/report.md)、[动作三路对照](../benchmark-results/motion-v2-kinetics/report.md)、[识餐报告](../benchmark-results/food-v1/report.json)、[RAG 报告](../benchmark-results/rag-v2/report.md)、[Agent 报告](../benchmark-results/agent-v2/report.md)。发生冲突时以可复算的原始评测、当次代码版本和验收日志为准。  
> 项目边界：一般成年人运动与生活方式管理；不是诊断、治疗或康复产品。现有暂停模型训练的决定继续有效。本方案规划训练条件，但不授权启动训练、购买数据、调用付费模型或发布生产版本。

## 1. 要赢得什么

### 1.1 作品主张

**HealthMate 是一个可追溯的个人健康行动助手：从真实纵向记录发现变化，说明依据和缺失，由用户选择一项短期行动，随后读取实际记录复盘；每一步可查看、可停止、可审计。**

参赛演示只围绕一个闭环：`真实记录 → 发现变化 → 说明依据与不确定性 → 两档行动 → 用户确认 → 真实进度 → 审慎复盘`。动作视频、识餐、RAG 和云边 Worker 服务于这个闭环，不能各自占据作品主标题。项目的创新是机制与系统集成创新，目前没有足够证据宣称原创基础模型、临床效果或高精度六动作识别。

### 1.2 竞争力判定

| 维度 | 当前状态 | 达到有说服力作品的证据 |
|---|---|---|
| 可辨识创新 | 行动账本、证据契约、用户确认和数据不足分支已进代码 | 陌生评审在 30 秒内能复述主张；一次真实演示能查到同一 `decision_id` 的全过程 |
| 可用产品 | 小程序、后端、Worker 和多条业务链路已有本地测试 | 两个真实账号、至少两台真机与弱网完成主流程、隔离和删除验收 |
| 技术可信度 | Agent/RAG 有离线测试；模型门控、队列恢复与审计存在 | 真实在线回答双人评审；独立动作集；所有低分、拒识和失败案例留档 |
| 用户价值 | 有提醒反馈与微实验统计接口 | 非医疗试用者能理解依据、作出选择并完成复盘；报人数、分母和退出原因 |
| 参赛表达 | 现有演示脚本覆盖功能较广 | 3 分钟展示一个真实闭环、一项对照、一项失败回退；材料与程序同版 |

以上是项目内部判定框架，不预估奖项。若报名“软件应用与开发”，以用户问题、可靠体验和工程闭环为主；若报名“人工智能应用”，还须提供更强的独立模型评测。赛事类别、原创期限、AI 工具使用和提交格式以目标赛事当届正式规则为准，不沿用旧届材料。

## 4. P0-1：冻结版本与统一证据

**目标：**评审材料、界面、代码与报告说的是同一个版本。

1. 建立 `docs/EVIDENCE_INDEX.md`：每个对外声明都链接对应报告、样本、日志、代码提交和限制，标记 `implemented / locally_verified / device_verified / production_verified / user_validated`；没有报告的声明标为“待验证”。
2. 修正文档漂移：当前 [旧架构文档](ARCHITECTURE.md)的迁移 head 与最新 `0022` 不一致；旧[演示脚本](COMPETITION_DEMO_SCRIPT.md)仍以视觉功能为重。新版材料必须指向本文件与最新功能汇总，历史材料保留原日期。
3. 为所有统计图展示样本量、时间窗与状态；无样本显示“暂无样本”，不展示 0% 或模拟成绩。
4. 冻结一个演示提交、依赖锁定文件、数据库迁移 head、Worker 模型配置、后端与小程序代码哈希。演示期间若修复缺陷，产生新版本和回归记录，不覆盖旧报告。
5. 清点提交材料：第三方数据、权重、用户媒体、密钥、数据库和历史压缩包不得混入；记录允许分发资产的来源及授权。

**验收：**抽取至少 10 条答辩表述，均能从证据索引直达同版本原件；报告可在干净测试环境按记录命令复算；不存在“门槛写成成绩”的页面或文档。

## 5. P0-2：把行动账本做成用户能理解的主创新

### 5.1 产品流程

首批聚焦 **运动断档** 与 **睡眠记录不足/睡眠时长变化**。首页一次只突出最相关的一条变化。提醒页固定回答四个问题：“为什么提醒我”“记录够不够”“今天可以怎么做”“不合适时如何停止”。用户选择温和/标准行动后，应先看到周期、目标、记录方式和停止条件，再确认启动。确认前不写实验数据。

当前[提醒页面](../miniprogram/pages/insights/index.wxml)已经有依据、两档方案、进度和历史行动；下一轮重点是降低术语负担。将面向普通用户的“AGENT V4 · 个人微实验”改为“我的短期行动”一类可理解文案，把模型版本、轨迹和原始概率留在评测详情中。空记录状态需说“目前没有足够记录判断”，避免把“没有记录”表达成“没有异常”。

### 5.2 数据和接口契约

在现有 `backend/app/services/agent/experiments.py`、`proactive.py`、`backend/app/api/v1/agent.py` 上扩展，不新建平行 Agent 系统。每个决策返回或可读取：

| 字段 | 要求 |
|---|---|
| `decision_id` | 服务端生成；关联信号、证据快照、方案版本、确认、进度与复盘；按用户隔离 |
| `facts` | 值、单位、记录时间窗、数据来源；推断值另标推断方法和版本 |
| `data_coverage` | 已记录天数与预期天数同时返回；缺失不得算作零运动或零睡眠 |
| `proposal` | 温和/标准两档、单一主指标、观察期、目标、停止条件、需用户确认 |
| `review` | 实际样本量、观察窗、`supports_hypothesis / not_supported_yet / insufficient_data` 与限制；不得写因果结论 |

把每条可执行建议标记为 `record_observation`、`knowledge_supported` 或 `general_guidance`。如使用知识来源，保存知识条目 ID 和引用版本；无命中时改为一般提示，不生成假引用。LLM 可负责表达，事实、停止条件和写入权限由确定性代码约束。

### 5.3 验收用例

- 正常案例：真实记录触发提醒，用户选择并确认，行动期间读取真实记录，到期生成含样本量的复盘；同一个 `decision_id` 可查全链路。
- 数据不足：缺失天数明确显示，复盘返回 `insufficient_data`，不把空记录判断为成功或失败。
- 放弃与停止：取消确认不创建实验；主动停止保留原健康记录并产生审计事件。
- 故障：DeepSeek 关闭时，基础提醒、规则建议、用户确认与停止仍能完成；失败状态可理解且可重试。
- 权限：另一账号查询该 `decision_id` 得到 404；导出与删除覆盖行动账本和反馈。

**代码落点：**`backend/app/services/agent/`、`backend/app/api/v1/agent.py`、`backend/app/services/privacy.py`、`miniprogram/pages/home/`、`miniprogram/pages/insights/`、`miniprogram/utils/insightPresentation.js`。只有现有字段无法稳定保存证据快照时才增加 Alembic 迁移，避免重复存储个人健康数据。

## 6. P0-3：真实 Agent 回答与安全评审

现有[Agent 离线报告](../benchmark-results/agent-v2/report.md)证明路由和接口契约，真实语言质量仍待验证。先冻结 33 条原用例，再新增一组不参与开发调参的陌生表达和对抗用例，覆盖缺数据、相互矛盾记录、疼痛/晕厥、药物调整、极端节食、来源不支持的结论、服务故障。真实在线回复逐条保留版本、时间、知识快照和脱敏文本。

两名独立评审者分别给“事实正确、引用支持、可行动、安全、易懂”打分，标注严重错误；意见不一致时保留原始两份评分，再由第三人裁定类别。现有 `backend/app/services/agent/human_review.py` 和模板可复用。修复后在**新的冻结复测集**和旧集上同时复评，避免只对失败题改到满分。

内部上线建议线：严重安全错误 0；事实正确、引用支持、可行动均分各 ≥4.3/5；安全均分 ≥4.7/5；两评审同维度相差不超过 1 分的比例 ≥85%。这些阈值是团队自定，不达标时保留低分案例并限制对应建议类别；不得以 RAG Hit@3 100% 代替回答质量。

**验收产物：**完整双人原始表、聚合报告、所有低分和严重错误、修复记录、模型与知识库版本、脱敏回复样本。付费在线模型调用和真人评审须在资源与人员就绪后安排。

## 7. P1-1：动作能力提升到可证明的竞争水平

### 7.1 明确目标

目标是**六类目标动作的自动识别**，评测默认流程对每段视频只提交一次预测；拒识、超时、处理失败计入全样本分母。动作次数、姿态错误提示和评分分别评测，不能用分类 Top-1 代表它们。Kinetics-400 当前只对部分目标动作有映射，不能直接把 400 类 softmax 当作六类准确率或可信概率。

内部候选启用条件：独立测试集全样本 Top-1 ≥80%、覆盖率 ≥90%、Macro-F1 ≥0.78、每类召回 ≥65%，且错误接受率、安全提示与 P95 延迟不比旧基线明显恶化。达到单项点估计仍须报告 95% 区间和测试集范围；不写成“对所有动作/所有用户准确率 80%”。

### 7.2 数据建设与防泄漏

1. 保留 REHAB24-6 的 120 段为历史对照，不再用它反复调阈值。其同一动作实例的双视角必须在同一划分中。
2. 新采集合规、知情同意的六动作视频。建议第一轮约 **240–360 段**，覆盖至少两种手机、正面/侧面、不同身形和光照，并收集少量遮挡、多人和未知动作负样本。这是采样计划，不是现有样本量。
3. 以**受试者为单位**划分开发/校准/最终测试，尽量令最终测试来自开发阶段未见过的受试者与设备组合。测试清单在调参前冻结并留哈希；同一原视频、切片、镜像、双视角不得跨划分。
4. 每段保存动作真值、是否可评价、机位、光照、遮挡、设备、受试者匿名 ID、原视频哈希及标注者。至少对争议样本双人复核，报告一致度和裁决记录。
5. 第三方数据/预训练权重登记许可和再分发边界；比赛交付只含许可允许的内容。

### 7.3 非训练阶段先做的工作

- 在同一独立集上运行现有规则、Kinetics 候选和安全融合实验；逐类看混淆、拒识和错误接受，而非只报平均值。
- 将错误归因到关键点丢失、机位不符、相近动作、开始/结束切片、遮挡、多人、非目标动作。先修输入质量判断、时间切片和错误映射等可复现问题。
- 规则阈值只能在开发/校准集调整，最终测试集只跑冻结版本一次。若反复查看最终测试结果，须另建真正未见过的终测集。
- 单独测 CPU/GPU 条件、P50/P95 总耗时、内存、失败恢复和真机上传时间。当前 24 段 CPU 推理 P50 约 100 秒，现场演示必须按真实时延设计等待和备份录像。
- `KINETICS400_OVERRIDE_ENABLED=false` 保持默认。候选结果显示模型来源、适用范围和拒识原因；无专属评分的动作不显示伪造次数或质量分。

### 7.4 可选训练路线与启用门禁

若以后恢复训练且数据许可、计算资源和独立集就绪，优先比较 **姿态序列轻量分类器** 与已有 SlowFast 六分类训练入口，而不是预设某一种一定更好。记录预训练权重、训练/验证划分、随机种子、超参数、模型哈希及成本；输出按受试者和场景分层的模型卡。训练只用开发集，校准只用验证集，独立测试一次性验收；模型无法证明增益时继续使用规则基线或拒识。

只有报告达到 §7.1 门槛、能力探测完成真实加载与前向 smoke、回退测试通过、模型登记 `release_status=active`，才可在灰度中考虑覆盖规则结果。任何开关变更须同时更新 UI、README、演示脚本和证据索引。

**代码落点：**`ai-worker/healthmate_worker/processors/motion.py`、`models/kinetics_runtime.py`、`evaluation/motion_benchmark.py`、`ai-worker/scripts/evaluate_motion_dataset.py`、`backend/app/services/model_governance.py`、`miniprogram/pages/media/`。训练入口仅作为将来条件性工作，不计入当前已完成量。

## 8. P1-2：真实环境、隐私与可靠性验收

建立一张可签字的验收表，每行记录日期、提交、环境、设备、账号、操作、预期、结果、截图/录像索引与复测结论。至少覆盖：

1. **两个真实微信账号**：登录、档案、行动账本、媒体任务、评测数据互相隔离；CloudBase 文件由平台权限验证仅创建者可读写。
2. **两台不同机型**：相机/相册权限、字体放大、长文本、安全区、上传取消与重试、后台切回、视频等待与结果刷新。
3. **弱网与服务故障**：超时、临时 URL 过期后原任务恢复、Worker 停止再启动、DeepSeek 不可用、重复提交；界面有等待上限和人工退路。
4. **数据库与发布**：在专用测试库与备份上验证当前唯一迁移 head、重复升级、旧数据保留；正式环境只在部署授权后执行，发布和回滚记录分开保存。
5. **隐私导出删除**：导出不含密钥/签名 URL；CloudBase 删除失败时不误报成功；对上传成功但注册失败的孤立文件建立对账。客户端删除回执不能写成服务端删除证明。

阻断项：跨账号访问成功、未确认写入、数据不足被当作正向改善、严重危险建议、核心流程在普通网络下不可完成。阻断项未解决前不声明正式上线验收通过。

## 9. P1-3：用用户研究证明价值，而非靠功能数量

### 9.1 可理解性对照

招募建议 12–20 名目标用户，使用脱敏的相同健康记录情境，对比“普通统计/泛化建议”和“HealthMate 证据—选择—复盘”两个呈现；随机交换顺序。记录用户能否说出提醒依据、缺失信息、下一步行动和停止条件，以及完成任务所需时间和错误。此对照只证明用户理解与操作差异，不证明健康效果。

### 9.2 七日真实试用

建议招募 20–30 名知情同意的非医疗场景成年人，先冻结指标与退出机制，再开始使用。统计：提醒查看率、行动启动率、到期复盘率、完成率、主动停止率、数据充分率、反馈“有帮助/不准确”分布、安全边界理解率。每项报告分子/分母、缺失与退出原因，样本很小时给出区间而不是强调百分比。试用不对疾病、体重下降或干预因果做承诺。

定性访谈重点问三件事：用户为什么选择或拒绝方案；是否相信“依据/我们还不知道”的解释；误判与等待最影响哪一步。把前五个高频问题转成产品修复项，复测同一任务，并保留未修复问题。

## 10. 识餐与其他能力的取舍

识餐当前是记录辅助。优先改进用户校正体验、份量不确定因素和区间展示；在独立的中式常见餐食与多菜拼盘集上测有效结果率、食材召回、区间覆盖与平均宽度、校正前后误差、完成校正所需时间。没有真实提升前，不将其放在主演示的技术高潮，也不宣传单图精确热量。RAG 和 Agent 的研发重点转向最终建议的事实与引用支持，避免继续只提高检索命中率。所有新增能力都必须服务于 §1 的主线。

## 11. 排期与退出条件

下表为 **4–6 周的团队工作估算**，受账号、评审者、设备和视频采集进度影响，不是赛事交付承诺。可并行准备数据与演示素材，但不得跳过前置门禁。

| 周期 | 主要工作 | 必须交付的证据 | 未通过时的处理 |
|---|---|---|---|
| 第 1 周 | P0 证据索引、文档统一、主线交互和两条演示案例 | 同版提交与报告；正常/不足案例的完整决策记录 | 暂停新增功能，先修断链与错误文案 |
| 第 2 周 | 双账号、两机型、弱网与隐私验收；真实 Agent 回复采集 | 验收表、失败录像、在线回复原件 | 未验收项明确标注；阻断项先修 |
| 第 3 周 | 双人评审、用户理解度对照、动作新集采集和标注 | 双人评分、理解度记录、数据清单与授权 | 严重错误先封锁对应建议；数据不足不报精度 |
| 第 4 周 | 动作独立集评测、错误修复、七日试用启动 | 同集对照、混淆矩阵、延迟、真实试用日志 | 模型未达线继续候选；演示不使用高精度措辞 |
| 第 5–6 周 | 完成七日试用、复评、封板、答辩演练 | 用户报告、证据索引、版本/交付清单、30 秒与 3 分钟脚本 | 依据实际结果收窄主张，不删负样本 |

若赛程只有一周，最小可交付范围是：**同版证据索引 + 一条真实行动闭环 + 数据不足案例 + 两账号真机验收 + 真实 Agent 小规模人工核查**。动作 80% 目标保持研发项，不因时间紧而改写现有报告。

## 12. 最终验收与答辩包

### 12.1 代码与质量

- 后端、Worker、小程序现有自动回归全绿；新增逻辑只补能发现真实故障的契约、权限和失败路径测试。
- 当前迁移 head 一致，干净库和旧库升级均可复验；生产数据不用于开发试验。
- Worker/云模型关闭时，健康记录、基础提醒、用户停止和隐私操作仍保持正确语义。
- 版本、模型、数据和报告哈希进入证据索引，未提交或临时结果不得写入正式成绩。

### 12.2 竞赛材料

1. 一页问题与主创新：一般用户为何需要“依据—选择—复盘”。
2. 一张架构图：小程序、后端、Worker、知识与行动账本各自职责。
3. 一条真实案例：记录、提醒、选择、确认、进度、复盘的同一 `decision_id`。
4. 一条失败案例：数据不足、模型候选不可靠或 Worker 故障时如何降级。
5. 一页量化证据：样本、分母、版本、指标和限制；同时展示动作/识餐的未达标结果。
6. 两段备份录像：在线主流程和故障回退；预置演示数据须在界面与讲稿中标记。
7. 原创与合规材料：团队工作分工、第三方依赖与数据许可、知情同意、隐私处理记录。

### 12.3 3 分钟演示顺序

`30 秒问题与主张 → 70 秒真实提醒和依据 → 45 秒用户选择、确认和账本 → 35 秒实际复盘与数据不足 → 25 秒真实评测与失败回退 → 15 秒边界与价值`。不在主演示中逐页浏览全部功能；动作识别只有在其最新真实报告达到相应门槛时才作为强性能证据展示。

## 13. 不允许混淆的结论

- 已实现 Kinetics-400 推理 ≠ 六动作准确率超过 80%；80% 是待检验的内部目标。
- 已通过本地回归 ≠ 微信云托管、真机、真实账号全部通过。
- Agent mock 指标 100% ≠ 真实在线回答正确率 100%。
- 3–7 天个人复盘 ≠ 临床试验、治疗效果或因果证明。
- 用户反馈“有帮助” ≠ 建议在医学上有效。
- 模型候选分值 ≠ 经校准的正确概率。

每次更新功能、评测或演示稿时，先更新本节相关口径和 §2 证据基线，再决定是否扩大作品主张。
