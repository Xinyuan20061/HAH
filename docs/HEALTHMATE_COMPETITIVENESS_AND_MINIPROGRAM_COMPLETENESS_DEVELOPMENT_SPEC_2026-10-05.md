## 0. 本文的权威边界

本文件是下一阶段**开发要求和验收标准**，不是“已经实现”的声明。它继承现有[低负担取证开发规格](HEALTHMATE_LUNA_LOW_BURDEN_EVIDENCE_DEVELOPMENT_SPEC_2026-10-05.md)和[全项目审计开发规范](HEALTHMATE_FIRST_PRIZE_FULL_AUDIT_AND_DEVELOPMENT_SPEC_2026-10-03.md)中未被当前代码取代的安全、授权、用户确认与证据追溯约束；需求文档中的命令、示例或旧审计结论均须与当前源码核对。优先级冲突时，以现行安全约束、冻结协议和当前真实代码合同为先，不为完成本文件绕过旧防线。

本次不开发 GPS 跑步，不将动作识别准确率作为主打卖点，不扩为“健康功能大杂烩”，不声称诊断、治疗、临床有效、个体因果改善或算法方法原创。小程序“完整性”指用户能从入口走到记录、解释、纠错、撤回、隐私操作，且异常能恢复；不等于每个页面增加新功能。

参考的研究与治理依据：2025 年 JMLR 关于[时间变化主动特征获取的评估](https://www.jmlr.org/papers/v26/23-1635.html)指出，部署取证策略会改变数据获取分布，因此离线结果与上线结果不能简单等同；[WHO 健康 AI 治理资料](https://www.who.int/publications/b/70584)和 [NIST 生成式 AI 风险管理资料](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)用于制定透明、可核查、持续评估的工程要求，不是本产品已通过认证的证据。

## 1. 一句话定位、故事与交付目标

**定位：HealthMate 是让普通人在不被频繁追问的前提下，完成一段可复核、可纠错、可撤回的个人健康行动周期的小程序。**

贯穿演示只讲一个问题：用户尝试缩短单次训练时长，七天里有漏记、拒答和事后更正。普通打卡产品会催填、补猜或继续展示过时结论；HealthMate 要能告诉用户“现在能确定什么、还缺什么、是否值得再问、后来改了记录为何必须撤回”，并在本人确认后生成新的复查版本。识餐、动作、聊天、计划、趋势等功能各自只作为入口、记录或解释层参与同一故事，不另立平行主轴。

建议统一的产品名词：

| 名词 | 对用户的含义 | 绝不意味着 |
| --- | --- | --- |
| 行动协议 | 本人确认并冻结的一段尝试 | 医嘱或自动训练处方 |
| 证据缺口 | 当前端点仍无法判定的已发生记录 | 用户做错、健康变差 |
| 低负担核查 | 预算内、一次一题、可拒答的补证 | 必须回答或实际耗时有硬限制 |
| 判断依据 | 绑定来源、规则、授权与知识版本的可重验说明 | 永久有效或医疗结论 |
| 修复 / 再复查 | 更正后先撤回旧判断，再本人确认新版本 | 静默覆盖历史或双重计入信念 |

主交付分为三层：① 可证明的取证质量—负担收益；② 有审核来源且不越权填个人事实的知识解释；③ 所有高频旅程在小程序真机可完成、可恢复、可撤回。任何一层失败，都不对外宣称“完整闭环已验收”。

## 3. 核心创新：从“多问几题”升级为“可维护的最小必要证据”

### 3.1 可被反驳的创新假设

H1：在**错误确定不增加**、有效判断覆盖不下降的前提下，按端点价值与真实可得性取证，可降低每个有效判断的累计询问数与交互时间。  
H2：来源修订后，版本绑定、同步撤回和按原槽修复，比丢弃整段周期重填减少修复成本，同时不复活旧判断。  
H3：审核知识若以“解释依据”而非“用户事实补全器”接入，可以提高用户对结果/限制的理解，同时不增加无依据的健康断言。

这是**待验证的产品与工程组合贡献**，不是主动问卷、证书、RAG 或规划算法本身的新发明。比赛叙事突出“漏记、拒答、修订条件下的判断维护成本”，新鲜感来自把停止询问、依据失效和再复查做成一个可见的交互机制，而不是模型数或功能数。

### 3.2 二级结构：证据债务，而非第二个独立产品

在核心闭环中增加一个**证据债务视图**：按端点显示仍缺哪些有效证据、现在是否可取得、谁控制下一步、询问是否值得、当前为何暂缓。它是判断状态的用户可读投影，不是单一“健康分数”；不得把缺失数或拒答数加权为健康风险。所有债务项必须有稳定 reason code、来源/时窗、可执行动作和过期规则。修复一条源记录时，视图自动重算；知识来源撤回时，解释依据变成“待复核”，不继续显示原引用为当前结论。

核心状态流：

```text
本人目标/冻结协议 ─→ 执行与负担两端点的当前证据
                           ├─ 已充分：停止询问，给可重验依据
                           ├─ 未到窗口：等待，不问未来事实
                           ├─ 已到且可补：预算内问一条，可拒答
                           └─ 冲突/过时：先修复，不猜值
有效复查 ─→ 来源更正/撤权/知识变更 ─→ 旧依据即时不可用
                                      └→ 本人按原槽修复 ─→ 预览 ─→ 本人确认新版本
```

## 4. 工作包 A：使取证策略真正有竞争力

### A1. 先做负结果诊断，不先“调参冲榜”

在 `benchmark/evidence-acquisition-v1/` 增加只读分析脚本，输入原 `report.json` 与 `traces.jsonl`，输出以下分层：各策略首次分歧的案例数、候选数/真正可选数、各剩余预算、oracle 初始状态、拒答与超时、问后标签变化、规划停止原因、目标端点、每条问答的边际有效性。必须回答：两步与一步为何完全同分？是候选同质、预算不足、未来配对分支缺失、固定先验与数据生成机制不匹配，还是服务层过滤后没有互补机会？在未得到诊断结果前，不修改阈值和报告口径。

原 v1 冻结文件和负结果只读保留；新实验写 `benchmark/evidence-acquisition-v2/`，独立记录数据、代码、配置、先验和报告哈希。

### A2. 评测定义覆盖完整用户问题

v2 数据生成与可审计案例清单至少包括：执行缺口、基线/跟进配对负担、周期窗口内外、本人拒答与未知、非随机缺失（MNAR）、来源更正/删除、知识撤回、证书失效与修复、重复请求/跨日预算。每类列出真实可得的候选和隐藏真值；病例级 split 按用户/周期分组，调参与最终测试集不共享人或周期。若用户数据未获知情同意，仍只用合成数据，不复制个人明文到仓库。

必须有同预算基线：当前生产门控、固定顺序、随机、熵优先、一步价值、两步价值、有限小状态精确参照；共同使用同一案例、响应随机量、真实预算约束和失败入分母。`fixed_fill` 仅为不安全反例，不能作为唯一对手。两步“互补案例”仍作为机制单测，不替代主端到端比较。

主指标为**每个正确且可核验的已确定端点的累计交互成本**（问题数和用户报告时间分别报告）；同时强制报告覆盖率、错误确定率、暂缓率、拒答率、P50/P95 耗时、修复成本和安全事件。不能靠一律暂缓换低错误，也不能把估算时间伪装成实测。比较以用户/周期为抽样单位给 95% 区间，预先固定主要对手、方向和阈值，报告所有失败案例。

### A3. 答复与成本模型升级

保留现有 `ResponsePrior` 声明先验作为冷启动，不把其 0.75 回答率等工程初值写成真实世界常数。新 `response_model.py` 建议输出不可变 `ResponseModelSnapshot`：

```json
{
  "schema_version": "response-model-v2",
  "kind": "declared_prior_or_consented_calibration",
  "version": "<semver+hash>",
  "population_scope": "session_duration",
  "sample_count": 0,
  "probabilities": {"answered": 0.75, "unknown": 0.10, "declined": 0.05, "no_response": 0.10},
  "latency_ms": {"p50": 4000, "p95": null},
  "calibration_state": "prior_only",
  "created_at": "<UTC>"
}
```

实施要求：先有知情同意及最小化事件日志；分别估计执行确认与主观负担回答的结果分布、拒答/无响应及耗时，不跨用户暴露原始问答；样本不足时收缩到声明先验并标 `prior_only`；模型必须带样本量、版本、有效窗口和置信区间。个体模型不是“健康效果模型”，只影响提问顺序和预计成本，绝不改变精确 oracle、冻结协议、硬预算和安全阻断。不能把未提问项当作“会回答”；在线观察存在策略选择偏差，应提供敏感性范围，未经设计的历史日志不能当作无偏反事实真值。

规划器可加入明确的终点价值、配对价值、修复价值和预算机会成本，但每一项要可配置、可冻结、可消融；仍守住候选 ≤12、单题响应分支 ≤6、显式计算时间上限。深度 2 若在完整 v2 主集仍无稳定收益，采用更简单的一步/规则策略作为产品默认；保留两步为受控场景可选能力，不把复杂度包装成优势。

### A4. 真实用户证据（先可用性，再效果）

首轮为经同意的小规模**可用性试用**：让参与者完成同意、调预算、答一题/拒答、改记录、看到撤回、确认再复查和隐私操作；记录任务完成、理解题、主观打扰程度、实际耗时及失败原因。建议内部目标为至少 12 名不同参与者、关键任务完成率 ≥90%，这只是预设工程门槛，不是统计上证明人群效果或现有成绩。试用前明确数据用途、可退出、删除路径和非医疗性质。

若要声称策略优于基线，须另设计安全候选集内的知情同意对照；预注册分组、样本量、停止规则和失败处理。仅有 deterministic 生产日志时，可做描述性校准和影子评估，不能推断“若问了另一题就会更好”。

## 5. 工作包 B：把 RAG 从“能检索”升级为“能负责地解释”

### B1. 先校正环境与版本事实

当前 `backend/app/services/rag/service.py` 为词法准入 + ONNX 语义重排/语义兜底的 `audited_hybrid_v2`；`embeddings.py` 在 ONNX 模型不可用或异常时使用字符 n-gram 哈希后备。部署必须返回或记录 `retriever_version`、`embedding_backend`（`onnx_bge` / `hash_fallback`）、`knowledge_snapshot_hash`。后备模式既不能崩溃，也不能继续引用“ONNX 模式的 90.2%”作为当前运行成绩。为两种模式各自跑同一冻结集，性能下降则明确降级提示或不提供生成式健康回答。

### B2. 审核知识扩展，按问题体系而非篇数扩张

知识范围优先支持现有行动协议与常见问法：一般身体活动、入门力量/耐力、热身恢复、膳食结构、训练负担、慢病/特殊人群的**转介边界**。每一条知识必须有 `source_key`、机构、原始 URL、章节、原文定位或许可允许的审核摘要、发布日期、审核人/时间、适用人群、排除条件、版本哈希、启用状态和复审到期日。旧条目不就地覆盖：新版本审核发布，旧版本保留审计记录，依赖该知识的旧解释/证书读取时重新核验。

不以“抓更多网页”代替资料质量；不得把未经审核论坛、商业软文、模糊的营养数据和模型自述纳入权威库。来源不可访问/撤回时先禁用或标待复核。现有 13 条是旧评测快照，不是未来扩容目标；新增条目的目标由覆盖盲点清单驱动。

### B3. 冲突与回答支持度

增设内部 `knowledge_claims` 与 `knowledge_conflict_reviews`（或等价结构化存储）：主张的主体/人群、条件、行为、结果、方向、强度、限定词、来源位置及审核状态。检索后的候选冲突仅做**提示与拦截**，不让 LLM 自动裁决医学真伪；状态限定为 `not_assessed / no_conflict_found_in_reviewed_claims / potential_conflict / reviewed_resolved / insufficient_sources`。`no_conflict_found...` 不等于“证实无冲突”。涉及训练建议或特殊人群时，`potential_conflict` 输出“资料存在差异/需专业咨询”，不生成看似确定的个体结论。管理员人工审核后，审计记录包含审阅者、日期、适用范围和被采用的版本。

回答层按**原子陈述**核验引用：每条健康事实必须映射到当次已检索的 `source_key + content_sha256 + excerpt/section`；模型不能凭空生成 URL。未找到支持片段、资料过期或冲突未决时，缩小表述或明确不答。用户个人执行/负担事实只能来自本人当前有效记录，不能从指南或模型补值。冻结协议门槛不能由外部指南热改。现有 `GET /api/v1/knowledge/search` 保持兼容；优先扩展现有 Agent 的 `knowledgeSources` 和解释追踪，而不是新建一条绕开 Harness 授权的聊天通道。

### B4. 正式评测

保留 61 条旧冻结检索集并新增不参与调参的口语/否定/冲突/过期资料/超范围集。分开报告：检索 Hit@K、无关问题拒绝、部署后备模式表现；最终答案的原子事实正确率、引用支持率、无来源断言率、适用人群错误率、冲突识别召回/误报、用户理解度。至少双人盲评并记录分歧裁定；不把检索 Hit@3=100% 叙述成回答准确率 100%。建议的内部发布门槛是：所评高风险不支持断言为 0、引用错配为 0；这是有限集上的工程门槛，不是线上零风险保证。

## 6. 工作包 C：小程序的“完整性”按旅程验收

继续保留当前两 Tab（健身房/小管家）与现有 28 页面；不为展示新概念盲目扩 Tab。首页“状态与下一步”作为主线入口，聊天作为解释/行动建议入口，策略页作为冻结协议与证据真值入口。以下改动优先做加法式导航和状态聚合，不重写成熟页面。

| 用户旅程 | 必备入口与结束状态 | 关键异常与恢复 |
| --- | --- | --- |
| 首次进入 | 登录→隐私/能力说明→状态页→选择要做的事 | 拒绝授权、无记录、服务不可用时仍可浏览一般知识，不假装已个性化 |
| 计划与协议 | 首页/聊天→计划依据→本人确认→协议冻结→周期页 | 重复点击只写一次；协议过时需刷新，不静默应用旧方案 |
| 每日执行 | 今日计划/周期→已发生机会→本人记录→反馈当前端点 | 未到时间不允许报告；未知/拒答不写未完成；弱网同 key 重试 |
| 低负担核查 | 显示“为何值得问”→一题答/不答→预算与下一步 | 离页暂停计时、返回续计；过期问题不提交；无预算不催填 |
| 复查与更正 | 端点分开预览→确认→历史→改原记录→旧判断撤回→再复查 | 来源冲突、知识撤回或权限变化时明确标过时，不留可点击的“当前有效”假象 |
| 知识问答 | 提问→简明答复→展开来源/适用范围/不确定性 | 无来源、模型后备、冲突、高风险问题降级；来源打不开提供审核资料标识而非编造链接 |
| 识餐与动作 | 拍照草稿→本人改正→确认入库；上传动作→排队→有限观察/回看 | 上传/Worker 失败可重试；未过评测门槛不展示强评分；过期素材显示真实状态 |
| 数据控制 | 能力暂停/恢复→导出→删除账户/媒体回执 | 删除失败显示仍需处理，不把客户端报告冒充云端完成证明 |

页面级任务：

| 页面/模块 | 具体改动 | 验收方式 |
| --- | --- | --- |

### 全 28 页的责任清单

“全小程序完整性”不能只测策略五页。按 `app.json` 当前注册清单，逐组建立页面 owner、入口/返回路径、API 依赖、降级状态和回归用例：

| 页面组（现有页面） | 在主故事中的责任 | 不可缺少的完成条件 |
| --- | --- | --- |
| `home`、`state`、`insights`、`trends`、`evaluation`（5） | 今天的状态、变化和能力边界，不另起未经证实的“健康分” | 数值带时间/来源；过时与无数据不画假趋势；评测页区分合成与真实 |
| `chat`（1） | 解释、审核资料、用户确认的行动提案 | 模型只读当前授权数据；写入必须走已注册的本人确认动作；来源卡可追溯 |
| `plan`、`goals`、`checkin`（3） | 目标、计划和日常执行的来源 | 改动能触发相关证据失效；离线/重复提交不制造两条记录 |
| `records/index`、`records/diet`、`records/exercise`（3） | 饮食与运动原始记录的查看、纠错、删除 | 记录更正后下游建议/证书不继续假装当前有效 |

这张清单合计 28 页。每页至少有一条“从哪来、做什么、去哪儿”的导航测试；业务数据页另有空态/过时态；写入页另有并发与幂等测试。`evaluation` 页对外展示的任何成绩必须有数据集、日期、模型/检索器版本和证据等级，不能把开发中指标显示为上线能力。

### 共用错误与恢复合同

| 稳定错误类别 | 前端动作 | 不允许的动作 |
| --- | --- | --- |
| 401/会话过期 | 重新登录后以原操作 ID 和原请求体安全续交 | 自动造新的写入 ID 后重复创建 |
| 网络超时/弱网 | 展示“结果待确认”，先查询或原 key 重试 | 直接显示失败并允许新 key 再写一遍 |
| 409 版本冲突 | 读最新周期/来源并展示变化，让本人重新确认 | 用旧页面值覆盖新版本 |
| 来源/知识过时 | 撤下当前依据入口，转修复/重新核验 | 继续展示“已确认支持” |
| 能力关闭或未授权 | 给出设置/删除路径，保持一般知识可读 | 把历史授权当作新询问许可 |
| Worker/模型不可用 | 显示排队、规则降级或明确不可用 | 伪造分析完成或无来源回答 |

所有主要页面具有加载、空态、部分数据、离线/弱网、权限不足、版本过时、失败重试和成功反馈。重要操作按钮需防连点且可读屏；长文本、小屏、系统大字体、浅色/深色差异和触达面积做真机检查。动效不是本轮创新目标；如实施涉及动画/WXSS，必须另按仓库相应 Skyline/WebView 规范核对，不因本任务擅自迁移渲染器。

## 7. 现有接口上的增量契约

现有 `/api/v1/policy/episodes/{episode_id}/acquisition/sessions`、`/api/v1/policy/acquisition/sessions/{session_id}/next`、`.../questions/{question_id}/answer`、证书/修复/再复查接口不改语义。所有写请求继续要求 `Idempotency-Key` 和 expected version；客户端永远不提交终点标签、协议门槛或服务器超时事实。

建议对现有 `GET /api/v1/policy/acquisition/sessions/{session_id}` 和 `POST .../next` 的响应**加字段**，旧客户端仍可解析：

```json
{
  "decision": {
    "action": "ask",
    "reason_code": "execution_endpoint_can_change",
    "explanation": "这条已到期记录可能改变执行判断；不回答也可以。",
    "endpoint": "execution",
    "confidence_kind": "exact_oracle_for_endpoint",
    "estimated_burden_ms": 3000
  },
  "evidence_debt": [
    {"endpoint": "execution", "state": "askable", "reason_code": "missing_due_report", "action": "answer_or_skip"},
    {"endpoint": "burden", "state": "waiting_window", "reason_code": "followup_not_due", "action": "wait"}
  ],
  "planner_meta": {"version": "<hash>", "response_model_kind": "declared_prior", "model_version": "<hash>"}
}
```

响应字段是服务端衍生视图，不能直接作为证书或裁决。禁止向用户显示伪精确的个体健康“概率”。`reason_code` 用稳定枚举，并配小程序映射文案；未知 code 采用保守“当前无法核查，请刷新”而不是继续提交。`estimated_burden_ms` 是预估，不是用户已花时间。

建议为内部知识工具 `policy.knowledge.read` 加审计字段：

```json
{
  "retrieval": {"version": "audited_hybrid_v2", "embedding_backend": "onnx_bge", "knowledge_snapshot_hash": "<sha256>"},
  "conflict_status": "potential_conflict",
  "claims": [{"claim_id": "<id>", "source_key": "<key>", "content_sha256": "<sha256>", "review_state": "reviewed"}],
  "allowed_use": "explanation_only",
  "may_fill_personal_facts": false
}
```

这只是内部工具/Agent 输出契约，不把模型返回当成数据库权威。`GET /api/v1/knowledge/search` 保持旧字段，新增运行后端/快照字段；前端引用卡只显示后端给出的真实 URL，不接受模型拼出的链接。

实现伪代码（决策路径保持单一、可测试）：

```python
snapshot = load_current_owned_snapshot(db, user_id, session_id)
require_consent_capability_and_live_versions(snapshot)
proofs = evaluate_endpoints_exactly(snapshot)  # execution 与 burden 不混算
if proofs.needs_repair:
    return explain("needs_repair", evidence_debt(snapshot))
if proofs.all_sufficient:
    return explain("sufficient", evidence_debt(snapshot))
candidates = filter_due_owned_audited_candidates(snapshot)
model = load_versioned_response_model_or_prior(snapshot.user_id)
plan = choose_next_with_frozen_budget(candidates, model, snapshot.contract)
return explain(plan, evidence_debt(snapshot))
```

事务约束不变：同用户 fence/行锁、唯一有效问题、同 key 同 payload 重放、同 key 异 payload 409、来源变更与旧证书失效同事务；读证书时仍重新核验，而不是只看缓存。知识审核状态变更不得使历史旧证书“复活”。

## 8. 数据、隐私、可观测性和迁移

新增持久化仅为必需字段：

1. `policy_response_model_snapshots` 或等价只追加版本对象：`user_id`（如确为个体模型）、用途、模型/配置哈希、样本量、校准窗、参数摘要、创建时间、失效时间。禁止保存用户原始聊天全文用于校准。
2. `knowledge_claims`、`knowledge_conflict_reviews`、`knowledge_review_events`：源版本、审核人/时间、适用范围、冲突状态及处理结果。知识管理权限与普通用户分离；不允许客户端提交“已审核”。
3. 评测结果优先放版本化脱敏文件/工件库，不把离线基准行塞入用户业务表；每份报告保留 dataset/config/code/knowledge/model 哈希。

每个新用户表加入所有权限制、导出与删除注册、FK 顺序测试和备份恢复计划。迁移从实际 `alembic heads` 追加，不改 0038 历史；先隔离 SQLite 结构测试，再对备份过的预发布 MySQL 演练升级、回滚/恢复和并发。降级若会丢新数据必须在运行手册写明导出或禁止直接降级。

运维观测至少记录：请求 trace、策略版本、知识版本、当前/后备 embedding 后端、问题发出与应答状态、预算命中、来源失效、修复失败、Outbox 积压、维护任务心跳、Worker 队列/预览可取率。日志只保留必要标识及哈希，不写 JWT、密钥、原媒体 URL、用户负担明文或完整健康对话。健康状态接口的“进程在线”与“链路可用”分开。

定时任务接线须验证 `worker/maintenance/policy-acquisition` 在部署环境真实运行：超时问题最终转态、补偿漏接失效、连续失败告警、任务重入幂等；GET 不承担清理或种子写入。账号删除与云对象删除必须有服务端可信回执或持续显示待核查，不把客户端自报当作完成证明。

## 11. 竞争力证明与答辩材料

最终演示只用一条连续用户故事：开始训练时长协议→有两天漏记→系统只问能改变判断的一条→用户拒答另一条→显示执行已充分但结果仍不足→后补负担自评→预览与本人确认→改正一条记录→旧判断立即撤回→只修复受影响的证据→新复查版本→展开知识来源与限制。演示每个状态都要来自真实接口/预置可复现数据，不能用静态卡片代替服务状态。若低负担策略 v2 尚未达到优势，演示仍可展示**克制停止、可拒答、可撤回**的可靠工程，不说“实测比基线省时”。

答辩证据包应包括：

1. 一页问题定义与方法差异：不是“AI 健身助手”，而是漏记/修订条件下的最小必要证据与判断维护。
2. 一张用户状态流、一个真实操作录像、一个可重放的来源更正/撤回案例。
3. v1 负结果与 v2（若已完成）对照/消融、数据哈希、置信区间和失败样本；如未达门槛如实说明默认策略选择。
4. RAG 检索和最终回答评测分开、来源审核台账、冲突案例、模型后备模式成绩。
5. 真机、目标数据库、Worker、云文件、隐私和故障恢复的验收清单；未验收项用醒目状态标明。

可合法宣称的最低版本：“已实现按需询问、端点隔离、版本绑定与修订撤回的个人行动证据闭环；软件测试与合成回放可复现，真实用户与部署效果仍在验证。”只有当预注册同预算主指标、真实试用和上线门禁分别通过，才逐层升级“少打扰”“可用”“可发布”的措辞。不能把 13 条知识、61 条查询、526/147 项测试或 363 个合成周期当作临床效果证据。
