# HealthMate 用户能力插件系统（V1）

## 1. 定位

HealthMate 的插件不是任意代码市场，而是“审核过的健康能力包”。用户只选择想获得的能力，不接触工具名、模型名和内部 Agent 术语。所有能力必须进入同一条证据门控闭环：

```text
目标 → 状态/上下文 → 候选能力 → 安全过滤 → 用户确认
→ 冻结协议 → 行为/结果证据 → 裁决 → 条件化个人记忆
```

这形成项目的核心差异化：新增能力不会新增一套互不兼容的推荐逻辑，而是接入同一个可验证、可撤销、可重放的个人决策内核。

## 2. 用户原则

用户界面使用“健康能力”或“能力中心”，不使用“插件管理”。每个能力必须说明：

- 它能帮用户解决什么问题；
- 需要读取哪些数据；
- 会产生什么结果；
- 哪些情况无法判断；
- 是否会产生行动提案；
- 如何暂停、关闭和删除数据。

启用能力只创建用户授权和配置，不自动执行高风险行动。关闭能力会阻止该能力的新读取、决策和提案，但允许用户完成已有周期的停止、复查和数据导出。

## 3. 插件契约

每个审核插件必须拥有稳定身份、版本、数据边界和用户价值说明：

```text
PluginManifest
  plugin_id/version/api_version
  title/summary/user_value
  data_needed/privacy_summary
  tool_names/action_names
  reversible/reviewed
```

插件只能提交：

1. 只读状态或证据；
2. 候选行动；
3. 结构化观察；
4. 用户确认请求；
5. 带版本和来源的裁决。

插件不能直接修改健康状态、个人记忆或裁决结果，不能把模型生成文本当作事实。

## 4. 理论基础

- 个体 N-of-1 与微型行为实验：建议必须有执行、观察和结束窗口；
- 受安全约束的上下文决策：硬约束先过滤，收益和信息增益只能在安全集合内排序；
- Beta-Bernoulli 条件化记忆：小样本收缩，按用户、上下文、指标版本隔离；
- 数据血缘与事件重放：源记录更正/删除后，相关证据和记忆可失效重算；
- Human-in-the-loop：模型提出候选，用户确认行动，系统记录真实结果。

V1 的裁决是描述性个人证据，不宣称医学诊断或严格因果证明。未来若引入随机推荐、延迟反馈或跨周期比较，必须新增预注册分析协议和独立评测。

## 5. 当前实现

- `backend/app/harness/plugins.py`：审核能力目录、用户启停、数据范围和工具门控；
- `backend/app/api/v1/harness.py`：`GET /harness/plugins`、`POST /harness/plugins/{id}/enable`、`POST /harness/plugins/{id}/disable`；
- `backend/migrations/versions/0032_harness_plugins.py`：用户能力授权与配置；
- `backend/tests/test_harness_plugins.py`：用户目录、可撤销和暂停门控测试。

当前内置能力包括健康状态、个人策略学习、动作证据、计划与结果。插件加载仍采用服务端审核的内置包，不允许用户上传任意可执行代码。

## 6. 竞争力验收

除了功能测试，还必须持续观测：

- 未授权能力调用阻断率；
- stale 证据进入决策的次数；
- 关闭能力后的新提案数；
- 结论可重放一致率；
- 用户完成能力启用所需步骤；
- 用户查看依据、暂停和撤销的成功率；
- 新能力接入已有证据协议所需时间。

项目的长期壁垒不是单个模型的分数，而是“能力扩展越多，证据、策略和用户控制越统一”的系统性优势。
