# HealthMate 最终工程收口与发布门禁（2026-10-03）

这份文档是本轮“大规模开发”后的唯一收口清单。它区分了“代码已经实现并由本地测试覆盖”和“必须在真实环境补证”的内容，不把占位能力、模拟 worker 或本地 SQLite 结果包装成线上能力。

## 1. 本轮已完成的产品闭环

### 1.1 用户体验闭环

- 识餐：选择图片 → 识别草稿 → 用户修正 → 用户确认 → 正式饮食记录。
- 饮食记录：记录页提供“查看明细”和按餐次/日期筛选；设置页新增“饮食记录”入口，解决已注册页面难以发现的问题。
- 动作反馈：上传、轮询、关键帧、时间轴、证据说明、重新分析和反馈均使用同一条结果链；证据不足时明确显示“暂未确认/数据不足”。
- 健康状态：状态页只读展示当前状态、数据缺口和下一步；写入动作交给小管家确认卡。
- 个人策略：候选 → 预览 → 周期开始 → 执行记录 → 结果回写 → 学习更新；支持停止、重置和版本冲突保护。
- 能力中心：设置 → 健康能力可以查看能力价值、数据范围、隐私边界，并逐项开启/暂停。暂停不删除历史记录，恢复可逆。

### 1.2 Harness 与插件边界

插件不是任意代码市场，而是审核过的健康能力包。当前内置能力：

| 能力 | 允许的数据 | 可逆操作 |
| --- | --- | --- |
| 健康状态 | 健康档案、饮食/运动/打卡 | 无自动写入 |
| 个人策略学习 | 目标、执行、结果 | 开始/完成/停止/重置 |
| 动作证据 | 本人视频和分析结果 | 无自动写入 |
| 计划与结果 | 计划、结果、反馈 | 只提议，不自动改计划 |

所有 Harness 工具继续经过 `ToolRegistry` 最小权限检查；插件暂停后，映射到该插件的工具统一返回 `PLUGIN_DISABLED`，写入动作仍必须经过用户确认协议。

## 2. 代码接口契约

### 2.1 小程序入口

- `GET /api/v1/harness/plugins`：返回用户可读能力目录。
- `POST /api/v1/harness/plugins/{plugin_id}/enable`：可选提交 `data_scope`，只能是能力清单中声明的数据范围。
- `POST /api/v1/harness/plugins/{plugin_id}/disable`：暂停能力，不删除历史数据。
- `GET /api/v1/harness/manifest`：供诊断和开发面板使用，同时返回能力目录。
- `GET /api/v1/health/energy-dashboard`：记录页能量概览。
- `GET/POST/PATCH/DELETE /api/v1/records/diet`：饮食记录查询、确认入库、编辑和删除。

插件接口的错误统一使用：

```json
{
  "error": {
    "code": "PLUGIN_SCOPE_INVALID",
    "message": "只能授权该健康能力声明的数据范围",
    "retryable": false,
    "request_id": "...",
    "details": {}
  }
}
```

### 2.2 数据与迁移

- 当前迁移头：`0032_harness_plugins`。
- 新表：`harness_plugin_installations`，按 `user_id + plugin_id` 唯一约束保存启停状态、版本、范围和时间戳。
- 隐私导出和删除已覆盖插件安装记录。
- 数据范围在服务层再次校验，不能只相信前端提交。

## 3. 本地验证结果

在本轮修改后应执行并记录以下结果：

```powershell
# 小程序静态/契约测试
node --test miniprogram/tests/*.test.js

# 后端全量测试
cd backend
.venv/Scripts/python.exe -m pytest -q

# 语法、迁移、隐私、OpenAPI 审计
.venv/Scripts/python.exe -m compileall -q app
.venv/Scripts/python.exe scripts/audit_migration_head.py
.venv/Scripts/python.exe scripts/audit_privacy_coverage.py
.venv/Scripts/python.exe scripts/audit_openapi.py

# 只检查当前连接数据库是否已应用全部迁移
.venv/Scripts/python.exe -m alembic check
```

已知本地结果：小程序全量测试为 `121 passed`；插件专项测试为 `3 passed`；上一轮后端全量测试为 `498 passed`。`alembic check` 对当前配置数据库仍会报告数据库落后于代码迁移头，这不是可以忽略的测试失败，必须在部署环境完成备份、迁移、回滚演练后再标记为通过。

## 4. 发布前强制门禁

以下项目没有真实证据时，发布说明必须标记为“未验证”，不能写成“已支持”：

1. 生产 MySQL/CloudBase 实际迁移和回滚；
2. CloudBase 文件删除的服务端回执与失败重试；
3. 真实识餐数据集（至少 100 张、不同光照/遮挡/中餐份量）及人工复核；
4. 真实动作视频集（至少 30 段、正反例和多视角）及双人复核；
5. 本地/云模型完整加载、标签映射和推理 smoke，而不只是 checkpoint 文件存在；
6. Agent 预算、拒答、提示注入和跨用户隔离的线上压测；
7. 微信真机授权、上传、后台切换、弱网和小程序包体验证；
8. 生产日志、指标、告警、trace_id 追踪和数据删除审计；
9. 数据库备份恢复、worker 停机、队列积压和上游不可用时的降级演练。

## 5. 不能在本地“假完成”的事项

- 不能因为本地 worker 能返回固定或模拟结果，就宣称动作/识餐达到竞赛级准确率。
- 不能因为插件目录可以开关，就宣称已经具备任意第三方插件沙箱；当前是审核过的内置能力包，尚未开放不可信代码执行。
- 不能把 `candidate_score`、模型名、内部工具名和 trace 诊断字段展示给普通用户。
- 不能把缺失数据当成 0，也不能在证据不足时给出确定动作类别、医疗诊断或自动处方。

## 6. 后续唯一允许的工程顺序

1. 在隔离的预发布数据库执行 `alembic upgrade 0032_harness_plugins`，验证备份和回滚。
2. 导入真实食物/动作评测集，生成带版本号的评测报告；不达门槛则保持 `pending/unavailable`。
3. 接通真实 CloudBase 与 worker，完成上传、删除、重试、超时和幂等演练。
4. 使用微信开发者工具和至少一台 Android、一台 iOS 真机完成关键路径回归。
5. 通过全部门禁后，才允许把能力状态从实验/待验证切换为可用。

## 7. 责任边界

HealthMate 的核心竞争力仍是“证据门控的个人健康策略闭环”：系统不仅给建议，还记录依据、约束、执行结果和用户反馈，并在证据不足时主动拒绝过度承诺。插件系统只是把这条闭环按用户授权拆成可暂停的能力包，不能绕过证据、隐私和用户确认边界。
